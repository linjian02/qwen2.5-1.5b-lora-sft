# 种子数据说明

## 两份文件的区别

| 文件 | 条数 | 用途 |
|---|---|---|
| `sample_sft.jsonl` | 17 | **few-shot 基准**。`gen_candidates.py` 默认读它做示例，决定了模型生成候选的格式与语气 |
| `seed33.jsonl` | 33 | **手写种子起点**。覆盖 33 个业务场景，每行对应规则表的一个 `R` 编号 |

两份加起来 50 条，**已全部通过事实溯源校验**。目标凑到 300 条以上，扩量依据见 `data/rules/operator_rules.md` 第四节。

## 这些数字是虚构的 —— 但不需要改

`seed33.jsonl` 里的资费、档位、时限、违约金、短信指令（`KTFSR`、`QXLL` 之类），
是**为这套数据集设计的虚构规则**，主体叫「星联通信」，与任何真实运营商无关。

**不需要换成真实业务值。** 原因：

1. 真实资费表属于公司资产，离职带走写进个人项目是合规风险，不是真实性加分
2. 这个项目要验证的是数据构造与评测方法，跟「59 元档含多少 GB」是真是假无关
3. 规则由自己定义，才能做严格的溯源校验——每个数字都能指出来源

完整规则表在 **`data/rules/operator_rules.md`**，`R01`–`R33` 与本文件行号一一对应。
被问到任何一个数字，正确答案是「这是我定的」，而不是去背某个真实套餐。

## 要改的话：三处必须同步

如果想让规则更像自己熟悉的业务，按这个顺序改，漏一步就会造出自相矛盾的脏样本：

1. `data/rules/operator_rules.md` 对应 `R` 段落
2. `seed33.jsonl` 同一条的 **input 素材**，字段逐条对应
3. `seed33.jsonl` 同一条的 **output**，凡是引用了被改数字的地方全部同步

然后必须跑：

```bash
python scripts/check_rules.py
```

## 必须保持的东西（这是模型要学的）

- 四段结构：`【开场】【核心权益】【办理引导】【限制说明】`，顺序不可乱，不可多出第五段
- 语气：口语化、不用「亲」「宝子」、不堆感叹号
- 每段的信息职责：开场复述问题 → 权益讲条件和好处 → 引导给具体操作路径 → 限制主动交底

## 一条容易违反的约束：不要让模型算数

素材里给「8,650 分、100 分抵 1 元」，模型会自己算成「86 块多」——这次算对了，下次就可能算错。
客服场景里算错就是报错资费。

**规则：需要结论值（折合金额、剩余量、总节省、还需几个月）时，把结论直接写进 input 素材。**

```diff
- 检索素材：积分余额=8,650 分；兑换比例=100 分抵 1 元话费；
+ 检索素材：积分余额=8,650 分；兑换比例=100 分抵 1 元话费（8,650 分折合 86.5 元）；
```

模型只负责把「86.5 元」说得像人话，不负责除法的正确性。这是 RAG 中「检索片段必须自包含答案」的原则，
也是 `check_rules.py` 的 C2 项在守的线。

初次跑这份数据时，50 条里查出 **12 处**这类问题（8650÷100、40−38.2、20×24、12−8 等），
已全部改为素材直接给结论。

## 一个判断标准

写完自问：**这段话能直接发给用户吗？**

如果不能——太书面、太长、像公告、缺了「怎么操作」——就是不合格的训练数据。
模型会把这个风格学走，后面评测再高也没用，因为读起来就不像人话。

## 校验

两道，都要 PASS：

```bash
# 1. 事实溯源：数字有无出处、四段结构、禁词、段长
python scripts/check_rules.py

# 2. 数据集质检：格式合规、去重、SimHash
python scripts/build_dataset.py --seed data/seed/seed33.jsonl --src data/raw --strict
```

看 `out/fact_check_report.md` 与 `out/dataset_report.md`，四段合规率必须 ≥ 95%。
