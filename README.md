# Qwen2.5-1.5B LoRA 微调：结构化话术生成与可用性评测

在 **单卡 RTX 3070（8G）** 上，用 301 条自建数据对 Qwen2.5-1.5B-Instruct 做 LoRA 指令微调，把自由发挥的对话模型约束成「四段固定结构、只用素材内事实、缺信息就明说」的话术生成器，并给出一套可复现的评测口径。

任务场景是运营商套餐/权益类客服话术。业务主体「**星联通信**」为虚构，全部资费、时限、违约金口径由本仓库的规则表定义，不含任何真实企业数据。

---

## 结果

评测集 100 条（从 301 条中留出，与训练集做 SimHash 交叉去重确认零泄漏），`gold` 列为人工答案，代表上限参照。

| 指标 | 基座 | **LoRA 微调** | 人工答案 |
|---|---|---|---|
| 格式合规率 ↑ | 0.0% | **100.0%** | 100.0% |
| 关键数字保留率 ↑ | 53.6% | **80.1%** | 87.8% |
| 数字幻觉率 ↓ | 3.5% | **1.6%** | 0.0% |
| P50 延迟 (ms) | 3856 | 7002 | — |
| P99 延迟 (ms) | 10544 | 9817 | — |

按难度拆分（37 条为「素材故意缺信息」难例）：

| 难度 | 条数 | 基座幻觉率 | 微调幻觉率 | 基座声明缺失 | 微调声明缺失 | 人工声明缺失 |
|---|---|---|---|---|---|---|
| 普通 | 41 | 4.6% | 1.1% | 0.0% | 2.4% | 0.0% |
| 困难 | 37 | 3.8% | 3.4% | 0.0% | **13.5%** | **62.2%** |

基座模型在「声明缺失」一列全是 0%，不是它做得好，而是它根本不按结构回答，也从没试图说「资料里没有」。

## 指标之外的问题（重要）

**1.6% 的数字幻觉率会让人误判。** 这个指标只统计正则能抓到的阿拉伯数字，人工抽查 9 条难例输出后发现：

- **9/9 条都存在素材未支持的断言**，其中 3 条与素材直接矛盾
- 典型错误：「积分和话费余额会跟着转过去」（素材写的是不随转）、「1 点抵 1 元话费」（素材是 100 分抵 1 元）、「5G 覆盖资料里没写」（素材里写了，反向幻觉）

根因：同场景的 9 条样本共用大段素材，模型学到的是「这个场景该说哪几句」，而不是「按当前素材组织语言」。遇到没见过的字段组合，它用预训练常识填空。

指标盲区：中文数词（「等几天」「两倍」）不入正则、0–10 小整数被当作噪音排除、缺少基于 NLI 的语义一致性校验。

**结论：格式对齐已经解决，事实对齐还没解决。** 详细分析见 [`out/error_analysis.md`](out/error_analysis.md)。

## 数据怎么来的

不用真实业务数据，改为**规则表驱动生成**：`data/rules/operator_rules.md` 定义 33 个场景（R01–R33）的资费、时限、资格条件、违约金口径，是唯一事实来源。

每条样本的**素材与答案由同一份字段表渲染**，因此「答案里的数字在素材里找不到」在生成阶段就不可能发生——这是数字幻觉率能压到 1.6% 的主因。

```
33 场景 × (1 条标准 + 3 条用户画像改写 + 3 条难例) = 231 条
+ 71 条手写种子（含 21 条难例）
→ SimHash 分 4 段桶去重后入库 301 条（难例 120 条，占 40%）
```

难例的 6 种缺失类型：缺资费、缺时限、缺资格条件、条件冲突、素材互斥、询问不支持的业务。标准答案不是跳过，而是在对应段落明说缺哪项并给出下一步。

### 事实溯源校验 `scripts/check_rules.py`

6 项检查，全部通过才允许入库：

| 检查 | 内容 |
|---|---|
| C1 | 四段结构完整、顺序正确、无空段 |
| C2 | output 中每个数字必须在 input 素材里有出处 |
| C3 | 指令码（如 `KT5G`、`QXSP`）必须在素材中出现 |
| C4 | 无模板腔禁词（亲/宝子/尊敬的客户…） |
| C5 | 单段长度下限 |
| C6 | 同值不同单位告警（素材 40GB、答案 40 元） |

C2 在首次运行时揪出 12 处模型自作主张的算术（`8650÷100`、`40−38.2`、`(69−49)×24`、`12−8`…）。处理原则由此固定为一条硬约束：

> **需要结论值时，把结论写进素材，模型只做语言组织。**

即 RAG 里「检索片段必须自包含答案」，计算留在检索层，不让模型碰。C6 是后续补的——纯数值集合比对会放过「素材 40GB、答案 40 元」这类同值不同单位的编造。

## 训练配置

选 1.5B 走 **BF16 全精度 LoRA 而非 4-bit QLoRA**：1.5B 权重仅 3.1G，8G 卡装得下，顺带绕开 `bitsandbytes` 在 Windows 上最常见的安装失败。

| 项 | 值 |
|---|---|
| 基座 | Qwen2.5-1.5B-Instruct |
| 方法 | LoRA（`q/k/v/o` + `gate/up/down` 共 7 模块） |
| r / alpha / dropout | 16 / 32 / 0.05 |
| 可训练参数 | 18,464,768（**1.182%**） |
| 精度 | bf16（3070 为 sm_86，原生支持） |
| batch / 累积 / 轮数 | 2 / 4 / 4 |
| 训练规模 | 92 步，224 秒 |

**为什么 r=16**：跑过 r=8/16/32 三组对照，验证 loss 为 `1.143 / 1.084 / 1.083`。r=32 参数量翻倍，loss 只降 0.001，故取 16。

**为什么 4 轮**：8 轮时验证 loss 从 1.121 回升到 1.377，明显过拟合；4 轮降至 1.084。

Qwen2.5-1.5B 用 GQA（2 个 KV head），`k_proj/v_proj` 输出只有 256 维而非 1536，算参数量时最容易算错——7 模块全贴是 1,846 万，不是 7,000 万。

## 快速开始

```bash
# 1. 环境（Python 3.11）
pip install -r requirements.txt

# 2. 事实校验 → 构建训练集（去重、格式检查）
python scripts/check_rules.py
python scripts/build_dataset.py

# 3. 切留出集（必须在训练之前）
python scripts/make_evalset.py split --n 100
python scripts/make_evalset.py check

# 4. 训练
llamafactory-cli train configs/train_lora_1.5b.yaml

# 5. 基座与微调模型各答一遍，再阅卷
python scripts/predict_local.py --model Qwen/Qwen2.5-1.5B-Instruct --out out/pred_base.jsonl
python scripts/predict_local.py --model Qwen/Qwen2.5-1.5B-Instruct \
       --adapter saves/qwen2.5-1.5b/lora/sft --out out/pred_sft.jsonl
python scripts/score.py --pred out/pred_base.jsonl out/pred_sft.jsonl
```

`configs/train_lora_1.5b.yaml` 里 `model_name_or_path` 默认指向本地路径，换成 HuggingFace ID 或你自己的模型目录即可。

**顺序不能颠倒**：`build_dataset → make_evalset split → 训练`。跳过切分会把留出集写回训练集，评测分数就全是假的。

Windows 下另有 6 个一键脚本封装上述步骤，见 [`docs/本地操作手册.md`](docs/本地操作手册.md)。Linux / macOS 可直接 `bash run_all.sh` 走完上面全部 6 步。

## 为什么不是 7B

| 模型 | 加载方式 | 训练占用 | 3070 8G |
|---|---|---|---|
| Qwen2.5-7B | 4bit | 约 9G | ❌ 爆显存 |
| Qwen2.5-3B | 4bit | 约 5G | ✅ 需额外装量化库 |
| Qwen2.5-1.5B | BF16 不量化 | 约 4.5G | ✅ 本仓库方案 |

Windows 桌面会占用约 1G 显存，8G 卡实际可用 6.5~7G。在 300 条规模上做格式对齐，1.5B 与 7B 的差距远小于预期，7B 反而更容易过拟合。

## 指标定义

| 指标 | 定义 | 方向 |
|---|---|---|
| 格式合规率 | 四段齐全、顺序正确、无空段的比例 | ↑ |
| 关键数字保留率 | 素材中应出现的数字，在输出中出现的比例 | ↑ |
| 数字幻觉率 | 输出中出现素材里找不到的阿拉伯数字的样本比例 | ↓ |
| 主动声明缺失率 | 难例题上明确说明「资料里没有」的比例 | ↑ |
| P50 / P99 | batch=1、贪心解码，同机同设置下测得 | ↓ |

口径实现在 `scripts/score.py`，可直接打开核对。P99 仅在相同硬件与 batch 设置下有意义，跨环境不可比。

## 已知限制

1. 语义层幻觉未被自动捕获（见上文），需人工抽查或引入 NLI 校验
2. 300 条数据只够做格式与口径对齐，不足以提升业务知识
3. Windows 下无 vLLM，推理用 Transformers batch=1，吞吐不代表生产环境
4. 规则表为虚构，模型输出不可用于真实客服场景
